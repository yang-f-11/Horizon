## [Tim Berners-Lee's 1998 Essay on Persistent URLs Still Resonates](https://www.w3.org/Provider/Style/URI) ⭐️ 8.0/10

Tim Berners-Lee published the essay 'Cool URIs Don't Change' in 1998, arguing that URLs should be stable and persistent to preserve web links over time. The essay has become a foundational reference for web architecture. The principle remains crucial because link rot—when hyperlinks stop working—still afflicts the web, affecting research citations, corporate sites, and everyday users. Understanding this essay helps engineers design URLs with longevity in mind. Berners-Lee included a historical note explaining that 'cool' was 1990s slang for good, and warned against choosing domains and paths based on 'coolness' rather than longevity. The article also touches on the use of redirects, though modern SEO practices have since formalized 301/302 handling.

hackernews · Klaster_1 · Aug 9, 14:32 · [Discussion](https://news.ycombinator.com/item?id=49231809)

**Background**: A URL (Uniform Resource Locator) is the address of a web resource; when a resource is moved or removed, old links break, a phenomenon known as link rot. Persistence techniques include PURLs (Persistent URLs), which provide stable addresses that redirect to the actual location. The essay is part of the W3C's style guidelines for hypertext design.

## [Prototyping compressed text revision histories in SQLite](https://simonwillison.net/2026/Aug/9/sqlite-text-history-prototype/#atom-everything) ⭐️ 7.0/10

Simon Willison prototyped storing full text revision histories in SQLite by bundling every previous version into a JSON array of strings and compressing it with zlib or Zstandard. With help from GPT-5.6 Sol Pro, he built experimental prototypes; 1,000 simulated revisions of a document produced 20.4 MB of raw text that compressed to 80.3 KB as a Zstandard-compressed JSON array. This approach could drastically reduce the storage cost of revision histories compared to traditional row-per-version designs, shrinking storage by over 250 times in the test. It may inform future SQLite-based tools such as note-taking apps, CMSs, or data exploration tools that need to keep full edit histories without prohibitive space requirements. To avoid decompressing and recompressing the entire array on every edit, the prototype splits history into multiple rows, each containing at most 128 revisions or 3MB of uncompressed JSON. The compressed history is stored as a BLOB column alongside an uncompressed JSON array of Unix integer timestamps; no benchmarks or real-world workload tests were provided, so this remains an unvalidated prototype.

rss · Simon Willison · Aug 9, 22:05

**Background**: SQLite is a widely used embedded relational database, and storing revision histories typically involves writing a new row for every version, which can quickly bloat the database for long documents. General-purpose compressors like zlib and zstd excel at removing redundancy, and compressing all prior versions together exploits the heavy overlap between successive text snapshots. Simon has previously worked on sqlite-history, which uses triggers to track table changes, and there are existing SQLite extensions such as sqlite-compressions and sqlite-zstd that bring compression and dictionary-based row-level compression directly into SQLite.
